Certora Failure Analysis

InvariantMind generated 6 invariants for zkWrapper and translated 4 to CVL. One rule contained:

to_mathint(zkWrapper.getLastRoot())

getLastRoot() returns bytes32, which cannot be cast to mathint in CVL. Certora exited with code 1 and produced 0 verification results. A via-ir retry was attempted but the error is in the spec, not in compilation.

Mitigation: Halmos verified 14/14 functions of zkWrapper via symbolic execution, partially compensating for the Certora failure. The InvariantMind bug (to_mathint on non-numeric return types) needs to be fixed in the framework.

#10034
Invariant Violation: Fee Rounding to Zero
False Positive
Medium Confidence: 0.50 Tool: invariant_violation_detector
For amounts < 400 wei, protocolFee = amount * 25 / 10000 = 0. The invariant netAmount < amount is violated when fee = 0.
False Positive — Ceaser uses fixed denominations (DenominationLib): 0.001, 0.01, 0.1, 1, 10, 100 ETH. Minimum denomination is 0.001 ETH = 1015 wei. For 1015 wei: protocolFee = 10^15 * 25 / 10000 = 2.5 × 10^12 (always > 0). Amounts of 300 wei are impossible by protocol design. DenominationLib.isValid() enforces this.

False Positive — UltraHonk verifiers check that the proof corresponds EXACTLY to the public inputs provided. #10043
Fee-on-Transfer / Deflationary Token Accounting Discrepancy
Real Vulnerability
High Confidence: 0.95 Tool: agent_zero_autonomous

In the shieldERC20 function (zkWrapper.sol, line ~285):

IERC20(token).safeTransferFrom(msg.sender, address(this), amount + protocolFee);
totalLocked[assetId] += amount;

If the registered token is a fee-on-transfer token (e.g., USDT on certain chains, PAXG, or any token with a transfer tax), the contract receives LESS than amount + protocolFee but records the full amount in totalLocked.

Over time, totalLocked will exceed the contract's actual token balance. When the last users attempt to unshield, the call to IERC20(token).safeTransfer(recipient, netAmount) will revert due to insufficient funds.

Impact: Medium-High. Depends on which tokens the owner registers. If only standard tokens are used (ETH, USDC, DAI), there is no impact. If a fee-on-transfer token is registered, the last depositors lose funds.

Recommended mitigation:

uint256 balanceBefore = IERC20(token).balanceOf(address(this));
IERC20(token).safeTransferFrom(msg.sender, address(this), amount + protocolFee);
uint256 received = IERC20(token).balanceOf(address(this)) - balanceBefore;
require(received >= amount, "Insufficient tokens received");
totalLocked[assetId] += received;

Note: PoC did not compile (2 attempts failed with Error 7576 — Undeclared identifier when trying to create a MaliciousToken mock). Vulnerability confirmed by static source code analysis.

Confirmed Vulnerability — Well-known DeFi pattern. Discovered autonomously by Agent Zero with 0.95 confidence. The shieldERC20 function does not verify the actual amount received after safeTransferFrom, leading to accounting desynchronization for fee-on-transfer tokens.

Protocol Security Strengths

  • Halmos verified 14/14 functions of zkWrapper — all pass symbolic verification
  • CEI pattern correctly implemented — nullifiers marked spent before transfers
  • nonReentrant + whenNotPaused on all state-changing functions
  • Fixed denominations (Tornado Cash model) eliminate rounding attack vectors
  • Two-tier rate limiting — per-block global + per-address per-hour
  • Permanent root history — O(1) lookup via mapping, roots never expire
  • ZK proof verification — UltraHonk verifiers are mathematically sound
