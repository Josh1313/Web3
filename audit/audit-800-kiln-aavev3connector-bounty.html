Audit Scope

The framework audited multiple Kiln OmniVault contracts across audits #795–#806. The AaveV3Connector (audit #800) is a connector module called via delegatecall from the main Vault. It implements the bridge between the vault and Aave V3 lending pool, managing deposits and withdrawals of user funds.

The Kiln OmniVault ecosystem consists of a main Vault contract (0x869855...3A72), a ConnectorRegistry, and multiple connector implementations for different DeFi protocols.

Reported Finding

KILN-01
maxWithdraw() Returns Total Aave Pool Liquidity Instead of Vault-Specific Amount
Reported to Cantina
Medium Likelihood: Medium Impact: Medium

The maxWithdraw() function in AaveV3Connector returns the total liquidity of the entire Aave V3 USDC pool (~$985M) instead of the vault's specific withdrawable amount (~$120K).

Buggy code:

function maxWithdraw(IERC20 asset) external view override returns (uint256) {
    // ... reserve checks ...
    (address _aToken,,) = _poolDataProvider.getReserveTokensAddresses(address(asset));
    return asset.balanceOf(address(_aToken));  // BUG: returns TOTAL pool liquidity
}

Correct implementation:

return IERC20(_aToken).balanceOf(address(this));
// address(this) = Vault via delegatecall = vault's actual aToken balance

Impact

  1. forceWithdraw DoS — The Vault's _maxRedeem() uses connector.maxWithdraw() to determine if a blocked user's balance is withdrawable. With the bug, it always returns "yes" (because $985M > any user balance), bypassing the InsufficientLiquidity safety check. When actual liquidity is insufficient, forceWithdraw reverts at the Aave level with an opaque error.
  2. ERC-4626 violation — Per EIP-4626, maxWithdraw MUST return "the maximum amount of the underlying asset that can be withdrawn from the vault by the owner." Returning the entire pool's liquidity violates this specification.
  3. Integration risk — Protocols reading maxWithdraw (lending, yield aggregators) receive a ~8,000x overstated liquidity figure.

Proof of Concept

// Foundry test on Ethereum mainnet fork

    address constant USDC = 0xA0b86991c6218b36c1d19D4a2e9Eb0cE3606eB48;

    function testMaxWithdrawIncorrectCalculation() public {
        IPoolDataProvider poolDataProvider = IPoolDataProvider(
            IPoolAddressesProvider(POOL_PROVIDER).getPoolDataProvider()
        );
        (address aToken,,) = poolDataProvider.getReserveTokensAddresses(USDC);

        // What maxWithdraw currently returns (BUGGY)
        uint256 buggyMaxWithdraw = IERC20(USDC).balanceOf(aToken);
        // Returns ~$985M USDC — the ENTIRE Aave V3 USDC pool

        assertTrue(buggyMaxWithdraw > 100_000_000 * 1e6);
        // A vault with $120K deposited reports $985M as maxWithdraw
    }
}
Confirmed — Reported to Cantina — The asset.balanceOf(address(_aToken)) call returns total pool liquidity instead of the vault's specific position. Fix: replace with IERC20(_aToken).balanceOf(address(this)). Submitted through Cantina bug bounty program. First accepted bounty from the framework.

Discovery Process

How the framework discovered this bug:
  1. The framework audited the AaveV3Connector as a deployed contract on Ethereum
  2. Math verification detected an anomaly in the maxDeposit calculation (#10716)
  3. Certora formally verified a view reentrancy violation (#10710)
  4. Manual investigation of related maxWithdraw function revealed the core bug
  5. PoC confirmed: USDC.balanceOf(aToken) returns ~$985M vs vault's ~$120K position
  6. Report submitted to Cantina — accepted by the Kiln team
